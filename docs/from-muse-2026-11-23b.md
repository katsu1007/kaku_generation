## (a) 区画番号（i）の付け替え：むぎ側の前提は壊れません

結論：**むぎ側（muse_kaku）の zones.js・polygonize.js・roomjudge は、どれも区画を「配列の位置」ではなく区画の `i` で持っている**ので、読み込み時にまとめて新しい `i` を振る分には食い違いません。くらちゃん側の読み込み順（まとめる→`orderFaces`→解析・ゾーン・補足区画）もコードで確認しました。その順番なら、解析の印（marks）もゾーンも補足区画も、まとまった後の区画集合から作られるので揃います。

コードで確かめた所（muse_kaku）：

- `js/zones.js`：ゾーンは `faces: [区画の i]` で持つ（`zones[best].faces.push(f.i)`）。位置ではない。
- `js/roomjudge.js`・`js/reader2/frame.js`：印（marks）は `marks[f.i]` と `i` がキー。
- `js/polygonize.js` の `supplementFaces`：区画の配列を形（重なり）で参照するだけで、`i` の対応表は保存しない。補足区画は別の物として作られる。
- `drawing.faceFix`（辺の手直し）・`faceOff`・`faceJoin`・部屋の `faces`：全部 `i` がキーだが、どれも読み込みの後に作られる物。facemerge は読み込み時に走るので、保存される区画集合は最初から「まとまった後」で、キーと実物は一致したまま保存される。

移植する時の注意（将来 facemerge を muse_kaku に持ってくる場合）：

1. **入れる場所は読み込み直後・解析の前**に固定すること。解析（`analyzeFrame`）の後に入れると、marks が古い `i` を指してずれる。保存済み案件の読み直しでは走らせない（保存された区画はまとめ済みで、faceFix 等はその区画集合に対するキーになっているため）。
2. **「分ける」時に `faceFix` の掃除も足した方がいい**。くらちゃん側の `faceSplit` は `faceOff`・`faceJoin` は消しているが `faceFix` は対象外。まとめた区画の `i` は「最大＋1」で振られ、その案件の中では二度と再利用されないし、`facerepair` は選んだ区画の `i` で引くので、今のところ実害は無い（記録が宙に浮くだけ）。ただ置きっぱなしは罠なので、消す対象に `faceFix[i]` を加えるのを勧めます。
3. 「分ける」の後にゾーンがまとめた区画の `i` を指したままになる件：むぎ側でも同じで、実害は無いと見ています。roomjudge はゾーンから「区画→ゾーン」の対応を作って区画の `i` で引くので、存在しない `i` は単に当たらない（ヒントが1つ消えるだけ。落ちない・違う部屋にもならない）。ゾーンは候補、という扱いで揃っています。

## (b) 階段ガードの設計

### まず実図面で階段の署名を測りました

5図面のうち階段が描かれている2件（ジェイテクト・大天）で、実線から測れた署名です。検出の作り：長さ 0.55〜1.8m の線を候補にし、平行（約3.5°以内）で、**長さ方向の重なりが短い方の70%以上**、等間隔に並ぶ4本以上の列を探す。

| 項目 | ジェイテクト | 大天工業 |
|---|---|---|
| 踏み面の本数 | 8本 | 4本 |
| 間隔（蹴上げ方向のピッチ） | 248mm（ばらつき最大15mm） | 250mm（ばらつき0） |
| 踏み面の長さ（階段の幅） | 1.1m | 0.9m |
| 列の長さ | 1.73m | 0.75m |
| 階段の区画 | 2.1㎡・名前なし（「階段」の文字が隣にある） | 3.0㎡・区画の名前が「階段」 |
| 上り・下り・UP・DN の文字 | **なし** | **なし** |

大事な対照実験：長さ方向の重なり条件を外すと、大天の事務所の机の列（等間隔に並ぶ平行線）が「10本・間隔235mm」の列として誤って拾われました。**重なり70%以上を入れると、3図面とも誤検出はゼロ**になりました。机・棚の列と階段の違いは「同じ長さの線が、同じ区間に重なって並ぶ」ことでした。

正直な限界も書きます。日本モウルド（工場）では、この検出で階段の列が1つも取れませんでした（線が長い・二重線など、描き方が違う可能性）。なのでこのガードは「効く所には効く網」で、全部の階段を保証する物ではありません。くらちゃんの工場の件で発火しなかったら、その階段の幾何（踏み面の長さと本数・間隔）を教えてください。数字をもらえれば帯を直します。

### ガードの案（facemerge の「まとめない条件」に足す形）

facemerge は今、線と文字を受け取っていないので、`mergeSplitFaces` に任意の引数 `segs`・`texts` を足す前提です（呼び出し側の project.js には両方あります）。

- **ガード階段1（名前・文字）**：中に入る区画の名前に「階段」を含む物がある、または試しの区画の中に「階段」「上り」「下り」「UP」「DN」の文字がある時はまとめない。——大天はこれだけで止まります。ただしジェイテクトのように区画が無名で文字が隣にあるだけの所は止まらないので、ガード2と併用が前提です。
- **ガード階段2（踏み面の列）**：上の検出で見つけた踏み面の列について、列の中心が試しの区画の中にあり、**列の箱の面積が試しの区画の 40% 未満**の時はまとめない。考え方：階段だけがまとまる（列が区画の大半を占める）のは階段室の組み直しなので通してよく、階段が広い所の一部として飲み込まれる時だけ止める。列がメンバー区画の境目をまたぐ場合も同じく止める（中心がどのメンバーにも入らず試しの区画にだけ入る時は、またいでいると見る）。

閾値の根拠：間隔 248〜250mm・ばらつき ≤15mm・踏み面 0.9〜1.1m・本数 4〜8 は**実測**。検出の帯（間隔 180〜330mm、ばらつき ≤35mm、長さ 0.55〜1.8m、本数 ≥4）と、ガード2の面積比 40% は**案（要測定）**です。40% の置き所：実測の階段区画は 2.1〜3.0㎡ で、飲み込む側の広い所はその数倍あるはず、という見積もりです。

### 間違えそうな所

- **誤って止める（false-block）**：机・棚・ロッカーの列が「重なり70%＋等間隔」を満たすと階段と誤認して、まとめるべき所を止める可能性。実測では重なり条件で全部外れましたが、同じ机が隙間なく並ぶ図面では残ります。緩和：ガード2は「列が試しの区画の40%未満」という条件とセットなので、家具で割れた大きい区画（列が大半を占める）では発火しにくい作りです。それでも江南の事務所（facemerge の看板事例）が止まるようなら失敗なので、下の確認に入れました。
- **取りこぼす（false-negative）**：幅 1.8m 超の広い階段、二重線の踏み面、見える踏み面が3本以下の部分的な階段、日本モウルド型の描き方。これらは素通りします（今の facemerge と同じ挙動に戻るだけ）。

### 直ったかの確かめ方（正解付き25枚で）

1. 工場の件：階段の上り口＋隣の広い所のまとめが消えること（その図面のまとめ件数がその1件分だけ減る）。
2. 25枚全部：合う部屋の数・器具の数と種類が、ガード無し facemerge と同じであること。
3. 江南の事務所のまとめが残ること（ガードの誤発火チェック）。
4. 名前が「階段」の区画が、どの図面でもまとめのメンバーにならないこと。
